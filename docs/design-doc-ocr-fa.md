# Design: OCR ساخت‌دار فارسی برای سازمان (Indra OCR + مهندسی بدون فاین‌تیون)

Generated by office-hours on 2026-11-02
Status: DRAFT
Mode: Intrapreneurship (Startup rules — internal org product)
Base model: Indra OCR (Datalab — ONNX، CPU، recognizer راست‌به‌چپ برای فارسی)

## Problem Statement

اسناد سازمانی فارسی (اسکن/PDF) با مدل‌های OCR عمومی دقت پایینی دارند. کاربران سازمان
الان دو راه دارند: (۱) ورود دستی اطلاعات (پرحجم) یا (۲) OCR موجود با دقت «خیلی بد».
نیش اصلی دقت پایین در **اعداد و کدها در جداول/فورم‌ها** است: کد ملی، مبلغ، تاریخ،
شماره پرونده. هدف، دقت بالا روی اسناد ساخت‌دار است — نه غلط‌گیری نثر آزاد.

## Demand Evidence

- بخشی از کاربران دستی وارد می‌کنند (هزینه نیروی مستمر) و بخشی از OCR موجود
  استفاده می‌کنند که طبق گفته خودشان «دقتش خیلی بد» است.
- درد ابرازشده به صورت مشخص: جداول و فرم‌ها؛ اعداد و کدهایی که خطا در آنها
  مستقیما بر رکورد مالی/حقوقی اثر می‌گذارد.
- مرحله فعلی: pre-product. آزمایش tiling انجام شده و نتیجه بهبود بوده
  (خروجی `*_ocr.txt` معمولی در مقابل `*_tiled_ocr.txt` در پروژه).

## Status Quo (وضعیت موجود)

سازمان اسناد ساخت‌دار (فرم، پرونده، جدول مالی) دارد که یا دستی تایپ می‌شود یا با
OCR ضعیف موجود عبور می‌کند و خرابی‌ها دستی اصلاح می‌شوند. هیچ مبنایی برای
اندازه‌گیری دقت وجود ندارد — و این خودش اولین شکاف است.

## Target User & Narrowest Wedge

- کاربر: واحدی از سازمان که اسناد ساخت‌دار (فرم/جدول مالی) را دیجیتال می‌کند.
- Wedge: یک **eval harness + ماژول تصحیح قاعده‌ای**: ۳۰-۵۰ صفحه واقعی سازمان +
  ground truth دستی + متریک (CER/WER برای متن، **field accuracy** برای هر نوع کد).
  Deliverable اول: اسکریپتی که روی یک فرم واقعی، خطای field را با عدد نشان دهد.

## Premises (تاییدشده توسط کاربر)

1. هدف اسناد ساخت‌دار (جداول/فرم/کدها) است، نه نثر آزاد فارسی.
2. بزرگترین اهرم دقت بدون فاین‌تیون، اعتبارسنجی/تصحیح قاعده‌ای تعیینی است (checksum ها).
3. هیچ تکنیک جدیدی بدون ارزیاب پایه اجرا نمی‌شود؛ هر تکنیکی که عدد ندهد کنار می‌رود.
4. قید CPU می‌ماند؛ تکنیک‌های وابسته به GPU رد می‌شوند (مگر به صورت آپشن ارزان بعدا).
5. بازخورد اصلاحی انسان جمع‌آوری می‌شود (دیکشنری سفارشی + دیتاست فاین‌تیون آینده).

## Approaches Considered

### A: حلقه تضمین کیفیت‌محور (کوچک‌ترین مسیر)
- eval harness (`evaluation/`) + ماژول post-correction قاعده‌ای (`persian_ocr/text/`).
- Effort: S (۱-۲ هفته) | Risk: کم
- -: سریع، عدد واقعی می‌دهد، بدون وابستگی جدید. -: حلقه انسانی ندارد، خطای متن آزاد را حل نمی‌کند.

### B: پایپ‌لاین ساخت‌دار + حلقه انسانی (انتخاب‌شده — با فاز اولِ A)
- Stage 1 (= A): ارزیاب + post-correction قاعده‌ای
- Stage 2: تشخیص جدول/فرم → **cell-level OCR** + انسمبل پیش‌پردازش (چند نسخه، انتخاب با conf)
- Stage 3: confidence-routing → صف مرور انسانی (UI کوچک) + جمع‌آوری اصلاحات →
  دیکشنری سفارشی سازمان (+ دیتاست فعال برای فاین‌تیون آینده)
- Effort: M-L (۴-۶ هفته) | Risk: متوسط (UI و فرآیند کاربر)

### C: تصحیح با LLM (رد شده فعلا — به دلیل قید CPU؛ به عنوان اپشن فاز بعد نگه داشته می‌شود)
تصحیح متن آزاد با LLM محلی/API + مسیر فاین‌تیون روی دیتاست جمع‌آوری‌شده. تنها پس از
A+B منطقی است.

## Recommended Approach

**B، شروع از فاز A:** اول ۱-۲ هفته عدد baseline را می‌سازیم؛ بعد بلوک ساخت‌دار
(cell-level OCR) و حلقه انسانی روی همان اسکلت.

## نقشه تکنیک‌های ارتقای دقت بدون فاین‌تیون (به ترتیب اولویت برای این معماری)

مرحله ۱ — قاعده‌ای (همین حالا):
- [x] Tiling با هم‌پوشانی + ادغام IoU/confidence — تست شده و برنده (در `persian_ocr/tiling.py`)
- [ ] نرمال‌سازی کاراکتری فارسی: ي/ی عربی↔فارسی، ك/ک، ارقام ۰-۹↔0-9، ZWNJ، کاراکترهای نامرئی
- [ ] تشخیص فیلد با regex (کد ملی ۱۰ رقمی، IBAN، تاریخ جلالی، مبلغ، شماره پرونده)
- [ ] اعتبارسنجی checksum: **کد ملی**، شناسه/کد اقتصادی حقوقی، **IBAN mod-97** — روش تعیینی:
      اگر جایگزینی درونِ کلاسِ ارقامِ درهم‌تنمه (مثل ۴/۶، ۹/۶ و مشابهِ درونِ فونتِ چاپی فارسی)
      نتیجه‌ای بدهد که checksum معتبر شود، آن اصلاح پذیرفته می‌شود؛ اگر نه، مورد به صف مرور انسانی می‌رود.
- [ ] تصحیح محدودشده با کلاس‌های درهم‌تنمه ارقام/حروف درون فونت چاپی فارسی (ب/پ/ت/ج و مشابه)
- [ ] eval harness + متریک + ground truth دستی (پیش‌شرط بقیه)

مرحله ۲ — پیش‌پردازش/ساختار (بعد از baseline):
- [ ] **انسمبل پیش‌پردازش**: binarization (Sauvola)، رفع سایه، sharpening، deskew؛
      اجرای OCR روی ۲-۳ نسخه پیش‌پردازش‌ شده و انتخاب خط‌به‌خط با confidence
- [ ] Re-OCR با DPI بالاتر فقط روی خطوط کم‌confidence (dual-pass ۲۰۰ → ۴۰۰ DPI)
- [ ] **cell-level OCR جدول‌ها**: بلوک‌های Table خود Indra یا مورفولوژی OpenCV؛ OCR هر خانه
      جداگانه + اعمال قواعد فیلدی هر ستون (بهترین راه برای فرم‌های جدولی)
- [ ] barcode/QR روی فرم‌ها (خیلی فرم‌های دولتی شناسه بارکد دارند) پیش از OCR
- [ ] دیکشنری دامنه: لیست نام/عنوان/کدهای واقعی واحد سازمان برای تصحیح نام‌ها و اصطلاحات

مرحله ۳ — حلقه انسانی و بعد از آن:
- [ ] confidence-routing → صف مرور انسانی (UI کوچک: تصویر کنار متن، اصلاح، تایید).
      در سنجش با هزینه خطای رکورد، مرور انسانی ارزان است — برای سازمان، «دقت نظام‌مند
      انسانی-در-حلقه» از دقت خام مدل عملی‌تر است.
- [ ] جمع‌آوری اصلاح‌ها: هر اصلاح انسانی → (تصویر، متن OCR، متن صحیح). در ماه‌های بعد:
      الف) دیکشنری سازمانی؛ ب) دیتاست آماده اگر روزی فاین‌تیون شد.
- [ ] (پس از همه) تصحیح با مدل زبانی کوچک/LLM — فقط اگر روی CPU اجرایی شود.

## Open Questions

1. حجم واقعی اسناد (صفحه در روز) و لیست انواع فرم — برای اولویت‌بندی مرحله ۲.
2. **مجوز مدل**: وزنه‌های Indra تحت **OpenRAIL-M** است (رایگان برای پژوهش/شخصی/
   استارتاپ زیر ۲۰ میلیون دلار). برای استقرار سازمانی، وضعیت مجوز باید بررسی شود —
   یا درخواست مجوز تجاری به Datalab داده شود. این یک ریسک حقوقی مسجل است.
3. شبکه سازمانی air-gapped است؟ (مدل‌ها local هستند و دانلود اولیه فقط یک بار لازم است،
   اما باید فرآیند حمل فایل بررسی شود.)
4. UI مرور انسانی: وب ساده جدا یا افزود در سیستم موجود سازمان؟
5. چه کسی برچسب‌گذاری ۳۰-۵۰ صفحه ground truth را انجام می‌دهد؟

## Success Criteria

- **متریک ۱:** field accuracy برای کدهای checksum-دار (کد ملی، IBAN): ≥ 99.5٪ روی eval set
- **متریک ۲:** CER خط متنی: بهبود %X % نسبت به baseline فعلی (تایل شده). X پس از
  اندازه‌گیری baseline تعیین می‌شود.
- **متریک ۳:** زمان مرور انسانی هر سند < X ثانیه (X با کاربر تعیین می‌شود)
- هر تکنیکی که تا ۱ هفته روی ارزیاب، A/B همه نتیجه مثبت ندهد، حذف می‌شود — بدون استثنا

## Dependencies

- برچسب‌گذاری دستی ground truth (۳۰-۵۰ صفحه) — حدود ۱-۲ روز کار متمرکز
- تایید مجوز OpenRAIL-M برای کاربرد سازمانی (یکی از Open Questions)
- استقرار مدل‌ها به صورت local (`INDRA_OCR_MODEL_DIR` — همین الان درست تنظیم شده)

## The Assignment (اقدام هفته جاری)

**در ۱-۲ روز آینده اسکلت فاز A را بسازید:** ۳۰-۵۰ صفحه واقعی و متنوع سازمان را
انتخاب کنید، ground truth دستی را کنار هر صفحه بنویسید، ارزیاب را بنویسید، و عدد
baseline تکنیک فعلی (tiling) را بیرون بکشید تا مشخص شود خطای الان دقیقا کجاست —
این عددها هستند که قدم بعدی را تعیین می‌کنند.

## What I noticed

- در آغاز گفتید «مدل‌های OCR عمومی روی متون فارسی قوی نیستند»، اما وقتی پرسیدم دقیقا
  کجا درد واقعی است، بلافاصله گفتید «اعداد و کدها در جدول/فرم». این تمرکز کل طراحی را
  از «فارسی عمومی» به «اسناد ساخت‌دار + قواعد تعیینی» تغییر داد — بهترین تکنیک نه مدل است، نه فاین‌تیون؛ قاعده است.
- جمله خودتان: «ساخت تست سناریوها و متریک‌ها خیلی مهمه» — نشان می‌دهد اولویت درست را
  خودتان می‌شناسید: بدون عدد baseline، همه آزمایش‌ها (شامل tiling) فقط «چیزهایی که
  احساس بهتری می‌دهند» هستند، نه نتیجه‌های اثبات‌شده. ارزیاب را جزو مرحله اول گذاشتم
  دقیقا به همین دلیل.
- رویکرد «فاین‌تیون نکن، مهندسی کن» را خودتان انتخاب کرده بودید و تاییدش کردم: تا وقتی
  tiling و پیش‌پردازش و cell-level OCR با ارزیاب A/B نشده‌اند، فاین‌تیون هزینه‌ای است
  که هنوز جواز ندارد.
